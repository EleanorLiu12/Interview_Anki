Q: Why is chunking needed? How do you trade off chunk size?
A:
Reasons: embedding models have input limits; one vector for a whole document dilutes its meaning; LLM context is limited.<br>
<ul><li><b>Chunks too small</b>: precise meaning, but missing context, and answers may be cut off</li>
<li><b>Chunks too large</b>: complete context, but the embedding is diluted, retrieval precision falls, and more tokens are used</li></ul>
A common starting point: 256–1024 tokens with 10–20% overlap; tune with an eval set. LlamaIndex defaults to <code>SentenceSplitter</code> with chunk_size=1024 and chunk_overlap=200 (adjustable through <code>Settings.chunk_size</code>).

Q: What is the difference between a bi-encoder and a cross-encoder?
A:
<ul><li><b>Bi-encoder</b>: encodes the query and document <b>separately</b> into vectors, then computes similarity. Document vectors can be precomputed → fast, suited to recall at massive scale. But there is no fine-grained interaction between query and document</li>
<li><b>Cross-encoder</b>: feeds (query, document) <b>together</b> into the model and directly outputs a relevance score. Highly accurate, but runs the model for every pair → slow, suited only to reranking a few candidates</li></ul>
Typical two-stage setup: bi-encoder recalls top-50/100 → cross-encoder (e.g. bge-reranker, Cohere Rerank) reranks to top-5.

Q: What ANN indexes do vector databases use? How does HNSW work?
A:
Exact kNN is O(N), so large scale needs <b>approximate nearest neighbors (ANN)</b>:<ul>
<li><b>HNSW</b>: a multi-layer graph (similar to a skip list); sparse upper layers navigate quickly and dense lower layers search finely. High recall and speed, but high memory use and slow builds. Q: What is hybrid search, and why is it needed?
A:
<b>Dense retrieval</b> (embeddings) is good at semantic similarity (synonyms, paraphrases) but poor at <b>exact matching</b>: proper nouns, product models, error codes, IDs, rare words.<br>
<b>Sparse retrieval</b> (BM25 / SPLADE) is good at exact keyword matching.<br>
Hybrid search: recall from both, then fuse the rankings → more robust recall.<br>
LlamaIndex: <code>BM25Retriever</code> + a vector retriever, fused with <code>QueryFusionRetriever</code>; or a vector store with native hybrid search (<code>vector_store_query_mode="hybrid"</code>, with an alpha weight).

Q: How does BM25 work?
A:
A classic term-frequency ranking function, an improvement on TF-IDF:<ul>
<li><b>IDF</b>: rarer terms get more weight</li>
<li><b>TF saturation</b>: more occurrences bring diminishing returns (parameter k1)</li>
<li><b>Document length normalization</b>: long documents naturally have more terms and are penalized (parameter b)</li></ul>
Pros: no training, interpretable, strong at exact keyword matching. Cons: doesn't understand synonyms or meaning.

Q: What is RRF (Reciprocal Rank Fusion)?
A:
A way to fuse multiple retrieval results using only <b>ranks</b>, not raw scores (scores from different retrievers aren't comparable):<br>
<code>score(d) = Σ 1 / (k + rank_i(d))</code>, with k commonly 60.<br>
Documents ranked highly in several lists score the highest. Simple, robust, and needs no score normalization.<br>
LlamaIndex: <code>QueryFusionRetriever(mode="reciprocal_rerank")</code>, plus modes such as <code>relative_score</code> and <code>dist_based_score</code>.

Q: What is ColBERT / late interaction?
A:
Sits between bi-encoders and cross-encoders: <b>every token</b> of the query and document is encoded into a vector (documents can be precomputed), and scoring takes each query token's maximum similarity with the document tokens, then sums them (MaxSim).<br>

Q: What is Small-to-Big retrieval? What are the two implementations in LlamaIndex?
A:
Idea: <b>retrieve with small chunks (precise) and generate with big chunks (complete context)</b>.<br>
<b>1. Sentence Window</b>: <code>SentenceWindowNodeParser</code> builds a node per sentence and stores the N sentences around it in metadata["window"]; after retrieval, <code>MetadataReplacementPostProcessor(target_metadata_key="window")</code> swaps in the window text.<br>

A:

Q: [Scenario] How do you answer global questions such as "summarize the common trends in these 50 reports"?
A:
Top-k vector retrieval only gets local fragments, so it doesn't suit <b>global/aggregate</b> questions. Options:<ul>
<li><b>Map-reduce summarization</b>: summarize each report (map), then summarize all the summaries (reduce): LlamaIndex <code>SummaryIndex</code> + <code>tree_summarize</code></li>
<li><b>DocumentSummaryIndex</b> / precomputed document summaries</li>
<li><b>GraphRAG</b>: entity graph + community summaries</li>
<li>Router: send detected summary questions to a summary engine</li>
<li>Have a long-context model read it directly (expensive)</li></ul>
